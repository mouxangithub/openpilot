# 7000（CarrotPilot 面板）与 5080（webui 子模块）融合分析

> 2026-10-12。基准：sp `E:/sp` branch `test` @ `5a231be18`。
> 所有数字来自仓库文件统计，未估算。相关前序：`docs/carrot-7000-settings-fusion.md`（设置目录统一，已完成）、
> `docs/carrot-port-parity.md`（端口对照）。

---

## 0. 结论速览

**两者不是"重复建设"，而是同一产品的两个入口，定位已经清晰，缺的是最后一层分工收口。**

| | 7000 CarrotPilot 面板 | 5080 webui 子模块 |
|---|---|---|
| 后端 | `sunnypilot/carrot/server/`（33 feature 模块，自有 aiohttp app） | `webui/server/`（98 条路由，bridge/ 56 模块） |
| 前端 | `carrot/web/`（源码 `src/` + 构建产物 `js/`，自有 esbuild） | `webui/web/static`（预构建产物，无源码在本仓） |
| 强项 | 行车画面（Vision/导航/AR）、Carrot 调参、dashcam/回放/终端/远程支持 | 设备设置（20 面板）、onroad 状态模型、模型/OSM/行程/存储/备份管理 |
| 现状 | **设备设置 20 组已齐**（§2），缺 `carrot` 枢纽 | 设置面完整，但**无行车画面** |

**融合已经发生了**，方式不是"合并代码库"，而是 **7000 单向代理 5080 的能力面**：
`features/opui_proxy.py` 把 `/api/opui/{tail}` 原样转发到 `127.0.0.1:5080`（可选依赖，daemon 不在则 502）。
今天 7000 的 Storage / Sunnylink / Firehose / Models / Vehicle / OSM / Trips / IMU / Torque / Developer
全部走这条通道，**没有一处重复实现**。

**所以"融合"要解决的不是"要不要合并"，而是两件事**：

1. **设置面收口**：7000 设备页与 5080 面板现在是两套渲染，靠人肉对齐（`DEVICE_GROUPS` 手写）。
   应改为**单一事实源**（5080 的 `panel_catalog.py` 或车机页面扫描）驱动，7000 只做渲染。
2. **行路状态补齐**：5080 有一套完整的 onroad 状态模型（`state_api.py::build_state_from_sm`，~590 行，
   70+ 字段），7000 的行车画面只渲染了其中一部分，**且有一处明确缺陷**：告警横幅的数据已经算出来但从未渲染（§5.1）。

## 1. 两侧架构

### 7000 — CarrotPilot 面板（端口 7000，always_run）

```
carrot_server.py → server/app.py::create_app()
  features/          33 个模块，各暴露 register(app)
    ├─ 自有能力：params / settings / dashcam / screenrecord / terminal /
    │            support_terminal / vision_diag / vision_test / bluetooth /
    │            carrot_navi / xiaoge / lan_services / static / ws / system
    ├─ opui_proxy.py   → 转发 5080（可选依赖）
    └─ unsupported.py  → 未移植项统一 501
  services/          参数、设置目录、设备信息、raw 中继、git 状态…
  web/               行车画面 + 设置页 + 日志/回放/工具（自有构建）
```

关键：**7000 是"驾驶面"的主入口**——它持有行车画面（`/ws/compact_state` + `/ws/raw*`）、
Carrot 调参、dashcam 与远程支持。这些 5080 没有。

### 5080 — webui 子模块（端口 5080）

```
webui/webuid.py → server/app_factory.py
  routes/__init__.py   98 条路由，全部挂在 /api/opui/*
  bridge/              56 个模块
    ├─ 设置面：panel_catalog.py（20 面板）+ params_api + param_constraints
    ├─ 设备面：device_api / network_api / bluetooth_api / storage_api /
    │          sunnylink_api / firehose_api / trips_api / osm_api /
    │          models_api / steering_api / ssh_api / agnos_api / imu_calibration_api
    ├─ onroad：state_api.py（状态模型）+ state_hub + ws_handler + ui_status +
    │          alert_resolve + dm_snapshot + model_overlay + cereal_services
    └─ 其他：onboarding / i18n / design_tokens / headless / webrtc
```

关键：**5080 是"设置面 + 状态面"的权威**——20 个面板的标签/范围/描述、
以及那套 70+ 字段的 onroad 状态模型都在这里。

### 数据来源是同一个

两者都从**同一套 cereal 消息 + 同一份 Params** 取数，差别只在打包方式：

| | 7000 | 5080 |
|---|---|---|
| 参数 | `UnifiedParams`（真 Params 优先，JSON 兜底） | `Params` 直读 |
| onroad | `/ws/compact_state`（C++/Cython 打包）+ `/ws/raw*` | `state_hub` 轮询 `SubMaster`，`build_state_from_sm` |

**这意味着融合不需要搬数据，只需要统一"谁来渲染"。**

## 3. 三种融合模式与取舍

| 模式 | 做法 | 优点 | 缺点 | 判断 |
|---|---|---|---|---|
| **A. 7000 全代理** | 7000 前端直接消费 `/api/opui/state`，不再自己算 onroad | 一套状态模型，零漂移 | 行车画面 1Hz 轮询不够；`/api/opui/state` 是 HTTP 快照，非流式；daemon 挂了行车画面全黑 | ❌ **不可取**（安全相关不能有单点依赖） |
| **B. 5080 嵌 7000** | 5080 面板里嵌 7000 的行车画面 iframe | 用户只记一个地址 | 5080 的静态产物无源码在本仓，改不动；跨源/鉴权复杂 | ❌ |
| **C. 各守其面 + 单一事实源** | 7000 保留自有流式 onroad（`compact_state`）；**渲染字段对齐 5080 的模型**；设置面改由 5080 的 catalog 驱动 | 无单点依赖；行车画面保持流式；设置不再人肉对齐 | 需一次性对齐工作 | ✅ **推荐** |

### 为什么 C 是对的

1. **行车画面必须能独立工作**。`compact_state` 是 C++/Cython 打包的流式通道（20Hz+），
   `/api/opui/state` 是 HTTP 快照。用后者做 HUD 会在网络抖动时闪断——安全相关 UI 不能这样。
2. **设置面本来就不需要两套**。7000 已经在用 opui 代理取数据，只是**渲染**还是自己写的。
3. **状态模型的字段定义**（哪个字段代表什么、极性、单位）应该只有一份。
   今天 7000 的 `hud_sp/payload.js` 和 5080 的 `state_api.py` 各有一份推导逻辑
   （例如 `deriveUiStatus` vs `_derive_ui_status`），**这是漂移风险**。

## 4. 推荐方案（模式 C）落地

### 4.1 设置面：把 7000 的分组声明改为"读 5080 的 catalog"

**现状**：`carrot/web/js/pages/setting_device_config.js` 的 `DEVICE_GROUPS` 是 20 条手写数组；
`SP_DEVICE_GROUP_IDS` / `SP_CAPABILITY_GROUP_IDS` / `DEVICE_EXTRAS_BY_GROUP` 三张手写 Set/Map。
5080 的 `panel_catalog.py` 里是另一份（38 个 id，含子面板）。

**做法**：新增 `/api/opui/panels`（5080 已有）的消费端，7000 前端启动时拉一次，
用它的 id/label/order 生成侧栏；手写表降级为**回退**（5080 不可达时用）。
`DEVICE_EXTRAS_BY_GROUP` 这类"哪个分组并入哪个基础分区"的映射保留手写——
它是 7000 特有的组织决策，不是 5080 的事实。

**收益**：5080 加面板，7000 自动出现，无需改 7000。

### 4.2 行路状态：对齐字段定义，补齐渲染

**第一步（必须先做）——消除双份推导逻辑**：
把 `ui_status`、`alert` 极性/尺寸映射、`speed_limit` 的判定，在 7000 侧改为
**照抄 5080 `state_api.py` 的语义**（不是复制代码，是复制判定规则并加注释指向来源）。
今天 `hud_sp/payload.js::deriveUiStatus` 与 `state_api.py::_derive_ui_status` 是独立实现。

**第二步——补渲染**（按优先级，见 §5）。

### 4.3 `carrot` 枢纽

5080 的 `carrot` 面板是个**入口页**：`CarrotWebEnabled` 开关 + 9 个子面板跳转 + 重置调参。
7000 把这些子面板的参数摊在了 `SUNNYPILOT` 节点下（`CARROT_SP*`），**功能不缺，缺的是"按 cp 的组织方式再看一遍"**。

**建议：不做。** 理由：7000 的 SP 分区已经是更好的组织（按车机页面分组，与设备屏一致），
再造一个 cp 风格的枢纽只会让同一个参数有两个入口。若确有用户习惯 cp 的导航方式，
低成本做法是在 7000 设置页顶部加一个**只读的"按 CarrotPilot 分组查看"视图**（纯前端重排，不改数据）。

## 5. 行路状态 UI 缺口清单（精确）

### 5.1 ⚠️ 告警横幅：数据已算出，从未渲染（真缺陷）

`hud_sp/payload.js` 已经构建：

```js
alert: {
  text1: String(selfdriveState.alertText1 || "").trim(),
  text2: String(selfdriveState.alertText2 || "").trim(),
  size: deriveAlertSize(selfdriveState.alertSize),
  status: deriveAlertStatus(selfdriveState.alertStatus),
},
```

但 `hud_sp/index.js` **没有任何 alert 元素**——全文件只有第 213 行一句注释提到 alert。
即：**openpilot 让驾驶员接管的提示（"TAKE CONTROL"等）在 7000 行车画面上不可见。**

这是本轮最该修的一条：数据链完整、渲染缺失、且安全相关。

### 5.2 其余 6 类

| # | 缺口 | 数据来源 | 复杂度 | 优先级 |
|---|---|---|---|---|
| 1 | 告警横幅 | `selfdriveState.alert*`（已在 payload） | 低（纯渲染） | **P0** |
| 2 | 设备状态条 | `deviceState.*`（已在订阅） | 低 | P1 |
| 3 | 驾驶员监控 | `driverMonitoringState`（白名单内，需加订阅） | 中 | P1 |
| 4 | 前车信息 | `radarState` / `modelV2.leadsV3` | 中 | P2 |
| 5 | 挡位/模式 | `selfdriveState.personality` / `carState.standstill` | 低 | P2 |
| 6 | 启动门 | `deviceState.started` + `managerState` | 低 | P2 |
| 7 | 道路模型叠加 | `modelV2`（5080 用 `model_overlay.py` 618 行） | 高 | P3 |

## 7. 风险与约束

1. **行车画面不能依赖 5080**。任何把 HUD 数据源改成 `/api/opui/*` 的方案都不可取（模式 A）。
   `opui_proxy` 是**可选依赖**，这是刻意设计——`features/opui_proxy.py` 在 daemon 不在时统一 502，
   页面回退通用渲染。
2. **5080 的前端产物无源码在本仓**（`webui/web/static` 是预构建），
   所以"改 5080 的界面"这条路走不通；能复用的是它的**后端 API 与 catalog 数据**。
3. **改行车画面逻辑必须设备验证**。本机缺 opendbc/zmq，`compact_state` 的字段只能静态核对。
4. **两侧的 `ui_status` 判定今天各写一份**，任何一侧改动都可能造成"同一场景两个面板显示不同状态"。
   §4.2 第一步就是为消除这个。

```bash
# 5080 路由总数
grep -cE "add_get|add_post|add_put|add_delete" webui/server/routes/__init__.py     # 98

# 5080 面板
grep -oE '"id":\s*"[a-z_]+"' webui/server/bridge/panel_catalog.py | wc -l           # 38（含子面板）

# 7000 设备页分组
grep -cE '^\s*\{ id: "' openpilot/sunnypilot/carrot/web/js/pages/setting_device_config.js  # 20

# 7000 已接的 opui 代理端点
grep -rhoE "opui/[a-z_/]+" openpilot/sunnypilot/carrot/web/js/ | sort -u

# 行路状态可用服务（compact_state 白名单）
sed -n '39,65p' openpilot/sunnypilot/carrot/server/services/raw_services.py
```
